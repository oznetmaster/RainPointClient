## Emulator compatibility evidence

| App build | Environment | Observed result |
| --- | --- | --- |
| 1.19.1065, original Google Play splits | Google Android 16 x86-64 with ARM64 translation | Native loader fails before the first screen. Remains unresolved. |
| 1.14.1047, publisher-signed standalone APK from [Uptodown](https://rainpoint-home.en.uptodown.com/android/download/1119362907-x) | Same Google emulator | Starts but demands an upgrade. Current version was subsequently restored. |
| 1.19.1065, exact original Google Play splits | Existing BlueStacks Android 9 instance | Signed-in navigation worked for this one-off inventory. Not a reusable test platform for this project. |

The Google emulator reports ABIs `x86_64,arm64-v8a` and native bridge `libndk_translation.so`. The installed ARM64 split contains `lib/arm64-v8a/libreactnative.so`, but the failure logs search APK paths under `lib/x86_64`. The package diagnostic records `primaryCpuAbi=arm64-v8a` and `extractNativeLibs=false`; Google Play did install the ARM64 variant. Follow-up inspection on 25 September traced the bundled `DirectApkSoSource` fallback-path builder to the first entry returned by `SysUtil$MarshmallowSysdeps.getSupportedAbis()`. That helper preserves the emulator's ABI ordering, filtered by process bitness. Fallback bytecode independently confirms index zero is used. On the recorded `x86_64,arm64-v8a` configuration, this constructs an x86-64 APK path despite the installed ARM64 split. This explains the observed incorrect lookup; it is not a verified repair or proof that no additional native-translation problem exists. Forcing the installer ABI alone would not change that loader choice. No APK was modified and no shared emulator properties were changed.

Both APK versions verified against publisher certificate SHA-256 `085ae9c4cadb4870a0eb48b10977019021e488b1a6b9e2dbe4b5b69444cae819`. The older APK SHA-256 is `e023dcc17bef1cdb81058ddf1a5b3728c28faa4b59ac442414fe3076da5cbbbf`. No package was patched or re-signed. The earlier APKPure connectivity and browser-safety failures are separate from this successful Google Play installation.

NUnit recorded installation, minimized capture, package diagnostics, compatibility comparison and restoration of the current package. A navigation-test pass only establishes guarded input/evidence capture; it does not assert that the app launched or that any capability passed validation. The interrupted guide step retained its reservation; its ownership was reconciled and the current sign-in screen inspected before continuing. No uncertain login or watering input was replayed.
